* Purpose

This repository documents and keeps track of Charm++ program runs
for my thesis. The performance numbers themselves are secondary —
what actually matters is the Projections *traces* the tracing-tagged
runs produce, since those are the dataset for a separate program I'm
writing to analyse Charm++ execution traces.

* Repository layout

- =building-charm.org= :: literate source for =build-charm.sh=, the
  SLURM job that builds PAPI, Charm++ (a plain build and a
  Projections+PAPI-instrumented build) and the Changa target.
  Tangle it to (re)generate the script.
- =bench_leanmd.org= :: literate source for =bench_leanmd.yml=, the
  JUBE benchmark definition for LeanMD. Defines a =base= tag (no
  tracing) and a =tracing= tag (Projections-instrumented, archives
  the trace on completion). Tangle it to (re)generate the YAML.
- =leanmd/=, =changa/= :: the benchmark program sources, as git
  submodules.
- =deps/= :: build-time dependencies (Charm++, PAPI), as git
  submodules.
- =runs/= :: one dated log per benchmark of the actual JUBE sessions
  run on Kabré — what was submitted, whether it completed, anything
  that went wrong. See [[file:runs/leanmd.org][runs/leanmd.org]].

Generated artifacts (=*.yml=, =*.sh=, JUBE's =*_bench/= output
directories, build byproducts under =deps/build*=, =deps/prefix=) are
gitignored; only the literate =.org= sources and the run logs are
tracked.

* Workflow

1. Tangle and submit =build-charm.sh= to build the dependencies.
2. Tangle the benchmark's =.yml= and run it through JUBE
   (=jube run ... --tag base= or =--tag tracing=).
3. Record what happened in the matching =runs/<benchmark>.org= file.

Trace archives are left wherever JUBE puts them (the numbered run
directory =jube run=/=jube info= reports, e.g.
=leanmd_bench/<id>/...=) — nothing copies or indexes them elsewhere,
so that reported directory is the actual path to pull traces from.
