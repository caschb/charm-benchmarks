#+title: Design Notes
#+author: Christian Asch

* Purpose

Why the build script and the two JUBE benchmark definitions look the
way they do. Each of =build-charm.sh=, =leanmd/bench.yml= and
=changa/bench.yml= used to be tangled out of a literate Org document,
and this file is where the prose from those documents now lives.
Short, line-specific rationale stayed behind as comments in the files
themselves; what needed more than a few lines is here.

Read this when a value looks arbitrary or a workaround looks
gratuitous. Most of them are neither, and several were paid for with
failed runs on Kabré.

The two benchmarks live in their own directories but share this file
rather than getting a =notes.org= each: the "Building Charm++" section
below is what both consume, and the ChaNGa section leans on it
throughout.

* Building Charm++

Source: [[file:../build-charm.sh][build-charm.sh]].

The script targets Kabré, but it is also meant to read as a guide to
building these variants on other systems: the SLURM preamble and the
module loads are the machine-specific parts, and everything below them
is not.

Kabré's login nodes are not the same as its compute nodes, so anything
that will run on a compute node is better compiled there too. Hence a
SLURM job rather than a plain script run on the login host. One node
is enough to build. The script assumes an MPI installation is
available and that the repo's submodules are already initialized.

PAPI is built first, following the instructions from the
[[https://github.com/icl-utk-edu/papi/wiki/Downloading-and-Installing-PAPI][PAPI wiki]], and installed into =deps/prefix=. Then four Charm++
variants are built into that same prefix, each skipped if it is
already present:

- =charm-base= :: plain =charm++= target.
- =charm-projections= :: =charm++= target with tracing and PAPI.
- =charm-changa= :: plain =changa= target.
- =charm-changa-projections= :: =changa= target with tracing and PAPI.

The naming is consistent on purpose: base variant name, with a
=-projections= suffix for the PAPI-instrumented tracing build.

** Why the Projections builds pass =-DZLIB=1=

Both Projections-enabled variants pass =-DZLIB=1=. That explicit
numeric =1=, rather than relying on the =ZLIB= option's default, is
what actually enables *gzipped* Projections trace logs (=*.log.gz=),
which keep the traces from filling our disk quota on long runs.

The subtlety is in how Charm++'s CMake build turns options into
=#define=s. =cmake/detect-features.cmake= iterates over every =CMK_*=
CMake variable and writes =#define <name> <value>= into
=include/conv-autoconfig.h= using the value *verbatim* (only ="" /FALSE=
become =0=, =TRUE= becomes =1=). =CMK_USE_ZLIB= is set to the =ZLIB=
option's value, and that option defaults to =ON=. So leaving =ZLIB=
unset emits =#define CMK_USE_ZLIB ON=; because =ON= is not itself a
macro, the C preprocessor evaluates =#if CMK_USE_ZLIB= (in
=src/ck-perf/trace-projections.C=) as =#if 0= and compiles the
compression path *out*. The run-time =+gz-trace= flag is then silently
consumed with a "not supported because Charm++ was built without zlib"
warning. Passing =-DZLIB=1= instead emits =#define CMK_USE_ZLIB 1=, so
=#if CMK_USE_ZLIB= is true.

This is precisely what Charm++'s own =./build= / =buildcmake= wrapper
does (it hardcodes =opt_zlib=1=). We do *not* migrate to that wrapper,
though: it has no way to turn on PAPI (it never passes =-DPAPI=), which
our tracing builds need. Staying on a direct =cmake= call, now with
=-DZLIB=1= alongside =-DPAPI=ON=, is what lets us have both PAPI
counters and compressed traces. An earlier attempt to force the macro
with =-DEXTRA_OPTS=-DCMK_USE_ZLIB=1= failed because
=conv-autoconfig.h='s =#define CMK_USE_ZLIB ON= is =#include=d into the
sources and overrides the command-line =-D=.

With =-DZLIB=1= the runtime compresses by default, so no =+gz-trace=
run flag is required at launch. See also "Why =+gz-trace= is not in
=args_exec=" below.

** The =tmp= symlink on the Changa variants

ChaNGa's =configure= derives =CHARM_PATH= from =charmc= and sources
=$CHARM_PATH/tmp/conv-config.sh=. Charm++'s CMake build keeps
=conv-config.sh= in =include/= and exposes it through a =tmp= symlink
pointing at =include/=, but its =install()= rules copy only =bin/=,
=include/= and =lib/=, not that symlink. A CMake-*installed* Charm++,
which is what this script produces, is therefore missing
=tmp/conv-config.sh= and ChaNGa's =configure= fails.

The script recreates the symlink in the install prefix for both Changa
variants, deliberately outside the "already built" guard so that
re-running it repairs an existing install without forcing a full
rebuild. It is done here rather than in the benchmark preprocess so it
is shared across workpackages instead of remade per run.

* LeanMD benchmark

Source: [[file:../leanmd/bench.yml][leanmd/bench.yml]].

A JUBE benchmark definition with two tags: =base= (plain) and
=tracing= (built with =-tracemode projections=, run with =+logsize=,
archiving the trace on completion). The tag-gated
preprocess/executable/args pattern and the shared system/input/exec
parameter sets are the template =changa/bench.yml= follows.

** The trace archive is a complete file set

Charm's =-tracemode projections=, used by the =projections= build
target in the tracing preprocess, writes exactly three kinds of file
per run: one =<pe>.log= (or =.log.gz=, gzip-compressed) per rank, one
shared =.sts= summary, and one shared =.projrc= config file. This was
confirmed against =deps/charm/src/ck-perf/trace-projections.C='s
~createLog~, ~createSts~ and ~createRC~. The postprocess globs
(=*.log* *.sts *.projrc=) cover that whole set, so the archive is
complete and self-contained by construction rather than by guesswork.
The =*.log*= glob deliberately covers both =.log= and =.log.gz=.

The archive is intentionally left in the workpackage's own JUBE work
directory rather than copied or indexed anywhere else. See
[[file:../leanmd/runs.org][leanmd/runs.org]] for where to find it for a given run.

* ChaNGa benchmark

Source: [[file:../changa/bench.yml][changa/bench.yml]].

Same tag-gated =base=/=tracing= structure as LeanMD. ChaNGa's build
differs in two ways that shape the preprocessing step:

1. It is autoconf-based (=./configure && make=, driven by a =CHARM_DIR=
   environment variable pointing at one of the Charm++ variants
   =build-charm.sh= builds), not a plain Makefile patched with =sed=.
2. It links against a second dependency, [[https://github.com/N-bodyshop/utility][N-bodyshop/utility]]'s
   =structures= library (Tipsy I/O), which ChaNGa's own CI workflow
   (=changa/src/.github/workflows/changa.yml=) clones as a sibling checkout
   and points at via =STRUCT_DIR=. It isn't vendored here, so it's
   pulled in as the =deps/utility= submodule.

** Why preprocess clones instead of using a =fileset=

=cha_commitid.c= is generated at build time by running =git describe=
inside the source directory, so a plain file copy, which is what
JUBE's =fileset= would do, loses the =.git= history that needs. We also
want each workpackage's build fully isolated from whatever another
concurrently running node-count/problem-size combination is doing;
configuring in place inside the submodule checkout would let concurrent
runs race on the same object files. So the preprocess clones
=changa/src= with =git clone --local= and copies =structures= fresh
into the workpackage.

One wrinkle: by the time preprocess runs, JUBE has already written its
job scripts (=submit.job=, =submit.job.in=) into the workpackage's
=work/= directory, which is the very directory the preprocess commands
execute in. It is therefore *not* empty, and =git clone --local
$source_dir .= would abort with "destination path '.' already exists
and is not an empty directory". Instead we clone into a =changa-src=
subdirectory, move just its =.git= into the work directory, drop the
now-redundant checkout, and =git checkout .= to restore the full
tracked tree, dotfiles included, alongside JUBE's untracked job
scripts. The result is identical to cloning in place, but tolerates the
pre-existing files.

** Keep the preprocess body free of commas

Learned the hard way across two failed runs. JUBE parses every
parameter value as a =separator=-delimited list, and that separator
defaults to a *comma*. So *any* comma in the preprocess body, even
inside a shell comment, splits the value, and only one fragment
survives the =$preprocess= substitution into =submit.job=. When this
bit us the build tail vanished and =mpirun= then failed on a
never-compiled =./ChaNGa=.

This is the same mechanism that intentionally turns =nodes: "1,2,4"=
into a sweep: desirable there, fatal in a script body.

Note the scope carefully. The constraint applies to text *inside* the
=_: |= block scalars, which becomes the parameter value JUBE parses.
YAML-level comments, the ones at the structural indentation outside
those blocks, are stripped by the YAML parser and never reach JUBE, so
they may contain commas freely.

** =testdata= and libtirpc

=testdata/Makefile= is a standalone, pre-autoconf Makefile whose recipe
(=$(CC) -o ppartt ppartt.c -lm=) hardcodes the compile line and
=#include <rpc/types.h>=. Modern glibc moved the SunRPC/XDR headers
into libtirpc (=/usr/include/tirpc=), so on such hosts that =make=
fails to find =rpc/types.h= even though ChaNGa's *own* =configure=
builds fine, since its =configure.ac= detects =tirpc/netconfig.h= and
adds =-I/usr/include/tirpc= and =-ltirpc= itself.

We can't inject flags through =CFLAGS=, because the recipe doesn't
reference it, so we override =CC= and =CXX= to carry the tirpc paths,
guarded on the header's presence so it is a no-op on older glibc.

** Why the tracing preprocess sets =CPATH= and =LIBRARY_PATH=

=configure='s =--enable-projections= toggles the =@PROJECTIONS@=
substitution in =Makefile.in=, but that alone isn't enough. Because
=charm-changa-projections= was built against PAPI, its =charm++.h=
pulls in =trace.h=, which =#include <papi.h>=. =charmc= adds a =-I= for
PAPI, but it is the path PAPI's =pkg-config= reported *when Charm++ was
built* (here a stale =/home/casch/papi/include=), not the =deps/prefix=
install that =build-charm.sh= actually produces. The header isn't found
and every ChaNGa translation unit fails to compile.

Rather than rebuild Charm++ to correct the baked path, the tracing
preprocess prepends our =deps/prefix= PAPI to =CPATH=, so =gcc= finds
=papi.h=, and to =LIBRARY_PATH=, so it finds =libpapi= at link. This
mirrors what LeanMD's tracing build does more directly via its =make
projections OPTS="-I.../include $(pkgconf --libs papi)"=. Both routes
just ensure the compiler sees the PAPI we built.

** Why =achInFile= is rewritten

=testdata='s generator writes =testdata.tbin= inside the =testdata/=
subdirectory, but its =testdata.param= refers to the input by the bare
name =achInFile = testdata.tbin=, which ChaNGa opens relative to the
launch working directory (the workpackage root, where =mpirun= starts
=./ChaNGa=) rather than to the param file's own location. The
preprocess therefore rewrites =achInFile= to =testdata/testdata.tbin=,
alongside the =nSteps= edit, so the run finds its input.

Launching from the workpackage root, rather than =cd=-ing into
=testdata/=, also keeps the Projections trace files where the tracing
postprocess globs for them.

That last point is load-bearing and easy to break. Projections derives its
=traceroot= from the *executable's* path, not from the working directory -- the
run log says so outright:

: Trace: traceroot: /data/casch/charm-stuff/full128/prj/ChaNGa

The JUBE runs are safe only because =executable= is =./ChaNGa= in the
workpackage root, so the two coincide. Run a binary from somewhere else without
=+traceroot= and the logs land beside the *binary*, silently overwriting any
trace already sitting there -- which is how a retained 128-step trace set was
destroyed on 2026-08-08. Any ad-hoc run outside JUBE needs an explicit
=+traceroot <rundir>=.

** Why =+gz-trace= is not in =args_exec=

Deliberately absent. With =charm-changa-projections= now built with
zlib enabled (=-DZLIB=1=, see "Why the Projections builds pass
=-DZLIB=1=" above), gzipped trace logs are produced by default, so the
flag is redundant. It also can never help on its own: on a Charm++
built without zlib, =+gz-trace= is silently consumed and ignored, which
is exactly why an earlier attempt to add it here had no effect.

** Parameter choices

- =nsteps= :: overridden into the copied param file during
  preprocessing, the same way LeanMD bakes its step count into
  =args_exec=. Kept as its own parameter here since it has to be
  spliced into a param *file* rather than passed on the command line.
  Tag-dependent since 2026-08-08: 128 under =cosmo=, 20 under
  =poisson=. cube300 is designed to integrate z=19 to z=0 in exactly
  128 steps, so truncating it would stop the run partway through
  structure formation.
- =problem_size= :: controls the =N= passed to =testdata='s generator, a
  Poisson distribution of =N= particles in a cubical volume. This is
  the scalable, synthetic input the ChaNGa README specifically
  recommends for performance benchmarking, mirroring how LeanMD's own
  input scales. That README notes =N=100000= takes about a minute of
  gravity calculation per step on a GHz-class core.

  =1000000= was dropped on 2026-08-08. It was by a wide margin the
  largest consumer of the 100 GB Lustre quota -- a trivial 20-step
  4-PE run at =N=10^4= already produced 200 MB of gzipped trace -- and
  it is the least informative cell in the sweep, because the
  statistical unit for the CCGrid work is the *chare-step*, which comes
  from TreePieces x steps rather than from particle count, while trace
  volume scales hardest with particle count. Under =cosmo= the
  parameter is a single fixed value (48^3 = 110592) since cube300 is
  one realisation and cannot be resized; it is defined only so the
  reference resolves and so the figure appears in JUBE's result table
  next to the Poisson runs.
- =gres= :: empty. We aren't building the CUDA target, since
  =build-charm.sh= only builds the plain MPI Changa variants, so no
  GRES request is needed.
- =timelimit= :: 40 minutes, bumped up from LeanMD's 20. ChaNGa's build
  (autoconf, plus compiling around 50 source files, plus the
  =structures= library) is heavier than LeanMD's single-Makefile build.
- =executable= :: =./ChaNGa=, untagged. The compilation process creates
  a symbolic link with that name pointing at the right binary for
  whichever variant was built.

** The initial-condition tags

Since 2026-08-08 a run needs a tag from each of two pairs:
=base=/=tracing= as before, and =cosmo=/=poisson= choosing the initial
condition. =cosmo= uses =testcosmo/cube300.param=, a real LCDM initial
condition committed in the ChaNGa tree; =poisson= uses the synthetic
cube =testdata= generates.

Tags rather than a swept parameter, because the two are separate
experiments rather than points on an axis. cube300 has a fixed particle
count and cannot be resized, so a parameter would have produced a cross
product with =problem_size= whose cells are mostly meaningless. The
contrast that matters is IC type at matched decomposition -- same
binary, same TreePiece count, same step count, only the physics
differing -- which is what makes =poisson= a control rather than a
second data point.

Measured on 2026-08-07: the Poisson cube is *not* homogeneous at grid
scale (it clusters harder than cube300 by raw contrast) but it is
homogeneous at *decomposition* scale, which is the scale that matters
here -- across 64 equal-count TreePieces the cosmological run shows
2.4x the density spread at z=0. Full derivation in the sibling
=ccgrid2027= repo's =notes/phase03-initial-conditions.md=.

Omitting an IC tag leaves =ic_param_file=, =ic_infile=, =ic_generate=,
=nsteps= and =problem_size= undefined, so JUBE fails loudly instead of
defaulting to one.

** Why =dEta= is overridden

Both preprocess bodies rewrite =dEta= to 0.03. That is not a tuning choice:
0.03 is ChaNGa's own shipped default (=ParallelGravity.cpp:299=), and
=cube300.param= ships 0.175, nearly six times looser.

At 0.175 cube300 barely multisteps. Measured over a 128-step 8-PE run on
2026-08-08, rung structure decays through the run and every step past 102 puts
all 110592 particles on rung 0. That is fatal for the CCGrid work rather than
merely slow: with one rung the multistep load balancer's per-rung history
degenerates to naive persistence and the active set is constant, so there is
nothing left to predict.

The mechanism is a clamp, not an absence. A particle's rung is
=ceil(log2(dDelta/dt))= with =dt = dEta*sqrt(eps/|a|)= and a floor at rung 0.
Scaling =dEta= scales every =dt= by the same factor, so it translates the whole
distribution rather than stretching it -- and a scan confirmed exactly that,
each halving lifting the identical shape up by one rung:

| dEta   | untraced 128 steps | substeps | rung populations at step 128 |
|--------+--------------------+----------+------------------------------|
| 0.175  | 83 s               |      259 | 110592                       |
| 0.05   | 166 s              |      882 | 98636 / 10939 / 1017         |
| 0.025  | 322 s              |     1763 | 68583 / 30053 / 10939 / 1017 |
| 0.0125 | 630 s              |     3526 | 8902 / 59682 / 30050 / 10941 / 1017 |

So the rung structure was always present in cube300 and the shipped =dEta= was
simply pressing it flat against the floor. Cost scales roughly with the substep
count; 0.03 lands between the middle two rows.

The rewrite deletes before appending, like =bParaWrite=, because the Poisson
param file has no =dEta= line for a plain =sed= to match. The
=/^dEta[[:space:]]*=/d= character class matters -- a bare =/^dEta/d= would also
delete =dEtaCourant=, =dEtauDot= and =dEtaDiffusion=.

** Forcing =bParaWrite = 0=

The preprocess deletes any =bParaWrite= line from the chosen param file
and appends =bParaWrite = 0=. At ChaNGa's default the parallel tipsy
write tears a contiguous block of records: fields shifted by one, file
length unchanged, so nothing downstream notices. Measured 2026-08-07 at
15 of 128 cosmological snapshots and 11 of 128 Poisson ones; =0= gives
0 of 128 in both. A single-species run has one mass value for every
particle, so a non-constant mass column is the detector.

Delete-then-append rather than a =sed= substitution because neither
shipped param file contains the key at all, so there would be nothing
for a substitution to match.

** No =fileset= in the run step

Unlike LeanMD's run step, there is no =fileset= in =use= here. The
source tree is pulled in by =git clone= inside the preprocess step
itself, not copied in beforehand by JUBE.

** Why =changa/src= points at a fork

The submodule tracks [[https://github.com/caschb/changa][caschb/changa]] on branch =thesis-instrumentation=,
forked from [[https://github.com/N-BodyShop/changa][N-BodyShop/changa]] at =v3.5=, rather than upstream directly.
ChaNGa is modified here: it emits a =SimulationStep= user event bracketing
each big step, which is what lets the trace-to-Parquet pipeline attribute a
traced execution to a timestep.

A patch file applied by the preprocess was the obvious alternative and is
wrong for one specific reason. =Makefile.in= generates =cha_commitid.c= by
running =git describe= (see "Why preprocess clones instead of using a
=fileset=" above), and =Cha_CommitID= is written into every run's ChaNGa
log. A patch applied after the clone is uncommitted, so =git describe=
would still report =v3.5-0-g98c212cc=: every traced run would stamp itself
as unmodified upstream ChaNGa while executing instrumented code. For runs
whose whole purpose is to be measured and reported, that is a provenance
defect, and an invisible one -- nothing looks wrong until someone tries to
reproduce it. With the fork, =git describe= names the instrumented commit
and each run's log self-identifies.

The second reason is operational: a patch that stops applying after a
submodule bump fails *inside* a Slurm allocation, once per workpackage,
against a 40-minute =--exclusive= reservation.

The fork is *private*, so unlike the other four submodules its =.gitmodules=
entry is an SSH URL rather than HTTPS: a private repository over HTTPS needs
stored credentials, and =git submodule update --init= would fail on Kabré
without them. =charm-benchmarks= itself is cloned over SSH there, so the key
is already in place. The other submodules stay on HTTPS because they are
public upstreams.

The fork keeps upstream as a second remote (=upstream=), so
=git fetch upstream && git rebase v3.6= is how a version bump is done. The
diff against upstream is deliberately additions-only -- no reformatting of
surrounding code -- so that rebase stays cheap; keep it that way.

** The timestep instrumentation

Lives on =ProjectionsControl=, the group ChaNGa already uses to drive
=traceBegin()=/=traceEnd()= per PE, and is broadcast from =Main=. It cannot
live in =Main= itself: =Main= is a mainchare and exists only on PE 0, so the
boundary would land in PE 0's log alone and executions on every other PE would
have no step to belong to.

There are two nested levels of bracket, =SimulationStep= around a big step
(broadcast from =Main::doSimulation()=) and =GravityPhase= around one iteration
of =Main::advanceBigStep()='s rung loop. The inner level is not decoration:
under multistepping a big step runs several gravity phases with different
active rungs, and the active set -- the thing the load balancer is predicting
-- only has a value within one of them. See "The physics side file" below for
the defect that established this.

=GravityPhase= brackets the whole loop iteration rather than just the gravity
call, because drift and both kicks belong to the substep too, and bracketing
gravity alone would leave every execution between phases unattributable.

Its =nestedID= is a run-global monotonic counter rather than a substep index.
=advanceBigStep()='s =currentStep= counts in units of 1/=MAXSUBSTEPS= with
=MAXSUBSTEPS = 1 << 30=, so =(step, currentStep)= cannot be packed into the
single =int= a bracket carries; a flat counter can, and is unique by
construction.

Three specifics worth not rediscovering:

- The step index travels in the bracket's =nestedID=, the only
  application-supplied integer a bracketed user event carries.
  =traceBeginUserBracketEvent()= *drops* it; the =NestedID= spelling is
  required.
- The guard is ChaNGa's own =-DCHANGA_TRACE_TIMESTEPS=, set in =Makefile.in=
  next to =-tracemode projections=, not Charm++'s =CMK_TRACE_ENABLED=. The
  latter is =0=/=1= via autoconf but is set from =${TRACING}= in the CMake
  build that =build-charm.sh= uses, so =#if CMK_TRACE_ENABLED= risks seeing
  the token =TRUE= and evaluating it as =0= -- silently compiling the
  instrumentation out of the build meant to carry it.
- The =base= tag compiles the broadcasts out entirely, so the untraced runs
  stay a clean perturbation baseline. The closing bracket is taken before
  =stepTime=, so the boundary's own cost shows up in ChaNGa's "Big step N
  took ..." line instead of hiding between steps.

The event names =SimulationStep= and =GravityPhase= are the contract with
=charmvz-cpp=, which resolves them through the STS =EVENT= registry. Renaming
either here means passing =-s <name>= there.

** The physics side file

ChaNGa writes =<achOutName>.physics.csv= when built with
=-DCHANGA_TRACE_TIMESTEPS=: one row per TreePiece per *substep*, gathered by
=CkReduction::concat= and appended by =Main=. This is the bulk half of the
carrier split -- substep boundaries travel in the trace as =GravityPhase=
brackets, per-chare physics travels here, and the two join on =(index,
phase)=.

CSV, converted to Parquet afterwards by =changa/tools/physics_to_parquet.py=,
rather than written as Parquet by ChaNGa. Emitting Parquet from the
application would mean linking Apache Arrow into ChaNGa's autoconf/charmc
build on Kabré and putting that write cost inside the run whose timings are
being measured. The file is at most =numTreePieces x nSteps= rows -- 160 rows
for a 5-step 32-piece test -- so its size is irrelevant beside a trace measured
in gigabytes, and being readable makes a wrong column obvious immediately.

The postprocess deliberately leaves it out of the trace tarball and does not
delete it, so it stays directly readable next to the archive.

Three things learned building it, all from runs that compiled and produced
plausible-looking output:

- *The sampling point was wrong for two runs.* =writePhysics()= was called from
  =doSimulation()= once per big step, after =advanceBigStep()= returned. The
  rung loop always winds back to rung 0 to close a big step, so every one of
  the 8192 rows of the first full run read =active_rung = 0= and =n_active ==
  n_particles= -- including steps whose run log reported three populated rungs.
  The numbers were not noisy or slightly off; they were the correct reading of
  the one instant in a step when the active set is trivially everything. There
  is no per-big-step value of the active set to record, so the call moved
  inside the rung loop and the row grain became the substep. This is why
  =physics_to_parquet.py= warns when a run has one active rung throughout: that
  condition is exactly what made the defect invisible.
- =TreePiece::boundingBox= is the *global* bounding box, not the element's own.
  The first version emitted it and every one of the 32 elements reported an
  identical box. The columns now carry the element's SFC key range -- the ends
  of its slice of the space-filling curve, which is what ChaNGa's equal-count
  decomposition actually splits on -- plus a real particle extent accumulated
  in the loop already being walked for the active count.
- =myNumActiveParticles= and =numActiveBuckets= are =#ifdef CUDA= members and
  do not exist in the CPU build, so both counts are recomputed inline the way
  =calculateNumActiveParticles()= and =startGravity()= do.

=tpLoad= is =getObjTime()=, the load Charm++'s own instrumentation measured for
the element. That column is the point of the file: it is ChaNGa's own estimate
and therefore the baseline a physics-based prediction has to beat.
