** Why not JUBE first

=bench-changa.yml= sweeps =nodes: 1,2,4= against =problem_size: 10000,100000,1000000=,
which is nine workpackages, each =--exclusive= with a 40 minute limit, and
each rebuilding ChaNGa from scratch inside its own allocation (the build is
in the =preprocess=, which the platform jobfile embeds in the submit script).
Since ChaNGa had never been built on this machine, a build failure would have
burned nine allocations to learn one fact. So the build and the traced run
were done by hand first, in a scratch directory, at the smallest size.

** [1] ChaNGa builds cleanly

Reproduced the =tracing= preprocess by hand into
=/data/casch/charm-stuff/changa-smoke= via =salloc ... srun=. Took about a
minute. Configure summary worth recording:

#+BEGIN_EXAMPLE
    Charm path        .../deps/prefix/charm-changa-projections
    C++ compiler      mpicxx
    Gravity Flags     -DHEXADECAPOLE -DCHANGESOFT -DDTADJUST -DMERGE_REMOTE_REQUESTS
    SPH flags         -DM4KERNEL=1 -DWENDLAND=0 -DM6KERNEL=0 -DCOOLING_NONE
                      -DDIFFUSION -DVSIGVISC -DGDFORCE -DJEANSSOFTONLY
    Misc Flags        projections=yes sanitizer=no
    Load balancer     MultistepLB_notopo
#+END_EXAMPLE

Two things to note:

- The binary is =ChaNGa.smp.prj=, an *SMP* build. That follows from the
  Charm++ variant being built with =-DTRACING_COMMTHREAD=ON=. It matters for
  launching (see below) and for the trace: =PROCESSORS= in the =.sts= counts
  =CkNumPes() + CkNumNodes()= in SMP mode.
- =-DDTADJUST= is on and the configured load balancer is =MultistepLB_notopo=,
  so multistepping (rungs) is active. That is the persistence baseline the
  CCGrid paper needs to beat.

The =libtirpc= workaround in the preprocess does fire on Kabré:
=/usr/include/tirpc/rpc/types.h= exists, so =testdata= is built with
=-I/usr/include/tirpc -ltirpc=. Without it the generator would not compile.

** [2] Do not nest mpirun under srun

First attempt at the traced run used =salloc ... srun script.sh= where the
script called =mpirun -np 4=. The job sat at 0% CPU for ten minutes with
*no ChaNGa ranks started at all* - only the wrapper and =mpirun= itself
appeared in =ps=. MPICH sees =SLURM_NTASKS=1= from the surrounding =srun= and
never launches.

This is not a ChaNGa problem and not a cluster problem. =bench-changa.yml=
already does the right thing: the platform jobfile calls =$starter= (=mpirun=)
directly from the batch script. Reproduce that shape when running by hand -
use =sbatch= with =mpirun= in the body, not =srun= wrapping =mpirun=.

** [4] Trace volume is the thing to worry about

*200 MB of gzipped log for 20 steps, N=10000, on 4 PEs.* That is a trivial
configuration by any measure, and it is already at the scale where the old
CARLA-era 80-PE LeanMD traces sat.

The JUBE sweep goes to =problem_size: 1000000= (100x the particles) on
=nodes: 4= at 20 tasks each (20x the PEs).

The quota makes this a *blocker*, not a caution:

#+BEGIN_EXAMPLE
  $ lfs quota -h -u casch /data
       Filesystem    used   quota   limit   grace
            /data  48.19G      0k    100G       -
#+END_EXAMPLE

*100 GB hard limit, 48 GB already used, so ~52 GB free.* A single large
workpackage plausibly exceeds all of it, and the sweep has nine. *The sweep
cannot be run as configured.* Something has to give before Phase 0.2's JUBE
step: cut =nsteps= for the large sizes, trace only a window of steps rather
than the whole run, shrink the sweep, copy each workpackage's tarball off
Kabré and delete it before the next starts, or ask for more quota.

Worth deciding deliberately rather than by trial: the paper needs
heterogeneity and over-decomposition, not raw particle count, so the largest
=problem_size= may not be earning its storage.

Related: ChaNGa writes its own =testdata.log= into the work directory, which
the postprocess =*.log*= glob will sweep into the trace tarball. Harmless for
=charmvz-cpp= (its log filename regex requires =.<digits>.log=, so it is
skipped) but it does bloat the archive and is confusing on unpacking.

** [5] End to end through charmvz-cpp

Pulled the trace to the laptop and ran the =charmvz-cpp= release build
(=refactor= branch, at =93daa69=). *22 seconds*, exit 0, all eight tables:

| table             |      rows |
|-------------------+-----------|
| execution         | 6,658,980 |
| message           | 4,232,000 |
| idle_interval     |    81,264 |
| migration_episode |     1,523 |
| entry_method      |       533 |
| chare_instance    |       234 |
| chare_collection  |        81 |
| processing_element|         4 |

Cross-checks against what ChaNGa itself reported:

- *32 TreePiece instances*, matching "Running on 4 processors/ 4 nodes with
  32 TreePieces" exactly.
- All 1,523 migrations are =TreePiece=; =LvArray= never migrates. Correct -
  TreePieces are what =Orb3dLB= moves. 30 of the 32 migrated, median
  =gap_us= 224.
- PAPI deltas populated on all 6.66M execution rows, zero nulls.

This trace is a much better exercise of the parser than the LeanMD ones,
because =TreePiece= is =ndims=1=: the pre-2026-08-06 code read a fixed four
index values and would have consumed =icputime= *and* PAPI counters as chare
indices. It also has real multi-word user event names with non-contiguous
ids, which until now only existed in synthetic unit-test fixtures.
