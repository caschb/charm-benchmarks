* [2026-08-06 Thu] First ChaNGa run on Kabré

Goal for the session was narrow: prove ChaNGa builds and produces a
Projections trace on Kabré at all, and that =charmvz-cpp= can read it. This
is Phase 0.2 of the CCGrid 2027 plan
(=thesis_stuff/ccgrid2027/notes/ccgrid2027-paper-plan.md=).
No JUBE sweep was run yet, deliberately, see "Why not JUBE first" below.

** Starting state

Everything needed was already in place from the LeanMD work:

- Repo at =/data/casch/charm-stuff/charm-benchmarks=, on =main= at =f2c6785=.
- All four Charm++ variants already built under =deps/prefix=:
  =charm-base=, =charm-projections=, =charm-changa=, =charm-changa-projections=.
- All submodules checked out (=changa= at =v3.5=, =deps/charm= at =v8.0.0=).
- =bench-changa.yml= already tangled, and verified byte-identical to a fresh
  tangle of =bench-changa.org= (the =.org= has a newer mtime, but that is a
  checkout artifact, not a stale =.yml=).
- No =changa_bench/= directory: no ChaNGa run had ever happened.

Note there is no =emacs= on Kabré, so the =.yml= cannot be re-tangled there.
Tangle locally and =rsync= the =.yml= up if it ever does drift.

** Why not JUBE first

=bench-changa.yml= sweeps =nodes: 1,2,4= against =problem_size: 10000,100000,1000000=,
which is nine workpackages, each =--exclusive= with a 40 minute limit, and
each rebuilding ChaNGa from scratch inside its own allocation (the build is
in the =preprocess=, which the platform jobfile embeds in the submit script).
Since ChaNGa had never been built on this machine, a build failure would have
burned nine allocations to learn one fact. So the build and the traced run
were done by hand first, in a scratch directory, at the smallest size.

** [1] ChaNGa builds cleanly

Reproduced the =tracing= preprocess by hand into
=/data/casch/charm-stuff/changa-smoke= via =salloc ... srun=. Took about a
minute. Configure summary worth recording:

#+BEGIN_EXAMPLE
    Charm path        .../deps/prefix/charm-changa-projections
    C++ compiler      mpicxx
    Gravity Flags     -DHEXADECAPOLE -DCHANGESOFT -DDTADJUST -DMERGE_REMOTE_REQUESTS
    SPH flags         -DM4KERNEL=1 -DWENDLAND=0 -DM6KERNEL=0 -DCOOLING_NONE
                      -DDIFFUSION -DVSIGVISC -DGDFORCE -DJEANSSOFTONLY
    Misc Flags        projections=yes sanitizer=no
    Load balancer     MultistepLB_notopo
#+END_EXAMPLE

Two things to note:

- The binary is =ChaNGa.smp.prj=, an *SMP* build. That follows from the
  Charm++ variant being built with =-DTRACING_COMMTHREAD=ON=. It matters for
  launching (see below) and for the trace: =PROCESSORS= in the =.sts= counts
  =CkNumPes() + CkNumNodes()= in SMP mode.
- =-DDTADJUST= is on and the configured load balancer is =MultistepLB_notopo=,
  so multistepping (rungs) is active. That is the persistence baseline the
  CCGrid paper needs to beat.

The =libtirpc= workaround in the preprocess does fire on Kabré:
=/usr/include/tirpc/rpc/types.h= exists, so =testdata= is built with
=-I/usr/include/tirpc -ltirpc=. Without it the generator would not compile.

** [2] Do not nest mpirun under srun

First attempt at the traced run used =salloc ... srun script.sh= where the
script called =mpirun -np 4=. The job sat at 0% CPU for ten minutes with
*no ChaNGa ranks started at all* - only the wrapper and =mpirun= itself
appeared in =ps=. MPICH sees =SLURM_NTASKS=1= from the surrounding =srun= and
never launches.

This is not a ChaNGa problem and not a cluster problem. =bench-changa.yml=
already does the right thing: the platform jobfile calls =$starter= (=mpirun=)
directly from the batch script. Reproduce that shape when running by hand -
use =sbatch= with =mpirun= in the body, not =srun= wrapping =mpirun=.

** [4] Trace volume is the thing to worry about

*200 MB of gzipped log for 20 steps, N=10000, on 4 PEs.* That is a trivial
configuration by any measure, and it is already at the scale where the old
CARLA-era 80-PE LeanMD traces sat.

The JUBE sweep goes to =problem_size: 1000000= (100x the particles) on
=nodes: 4= at 20 tasks each (20x the PEs).

The quota makes this a *blocker*, not a caution:

#+BEGIN_EXAMPLE
  $ lfs quota -h -u casch /data
       Filesystem    used   quota   limit   grace
            /data  48.19G      0k    100G       -
#+END_EXAMPLE

*100 GB hard limit, 48 GB already used, so ~52 GB free.* A single large
workpackage plausibly exceeds all of it, and the sweep has nine. *The sweep
cannot be run as configured.* Something has to give before Phase 0.2's JUBE
step: cut =nsteps= for the large sizes, trace only a window of steps rather
than the whole run, shrink the sweep, copy each workpackage's tarball off
Kabré and delete it before the next starts, or ask for more quota.

Worth deciding deliberately rather than by trial: the paper needs
heterogeneity and over-decomposition, not raw particle count, so the largest
=problem_size= may not be earning its storage.

Related: ChaNGa writes its own =testdata.log= into the work directory, which
the postprocess =*.log*= glob will sweep into the trace tarball. Harmless for
=charmvz-cpp= (its log filename regex requires =.<digits>.log=, so it is
skipped) but it does bloat the archive and is confusing on unpacking.

* [2026-08-08 Sat] First JUBE run of =bench.yml= - cancelled, =+logsize= is wrong

The first time =changa/bench.yml= has ever gone through JUBE; every earlier
ChaNGa run on Kabré, including all of 2026-08-07 and -08, drove =mpirun= by
hand. Run as:

#+begin_src sh
jube run changa/bench.yml \
     --include-path /data/casch/.local/share/jube/platform/slurm \
     --tag tracing cosmo
#+end_src

** The definition itself is fine

Worth stating plainly, because this is what the run was for. =jube --debug run=
expanded to the expected 3 workpackages, and the generated =submit.job= was
complete and untruncated - every =sed= rewrite survived including the new
=dEta = 0.03= one, so the comma rule held. All three workpackages built ChaNGa
from the cloned submodule without incident, jobs 598728 (1 node) / 598729 (2) /
598730 (4). Two ran; the 4-node one never left =PENDING (Resources)=.

Also confirmed in passing: the projections Charm++ is SMP, and =mpirun -np 20
./ChaNGa= without =+ppn= gives 20 ranks x (1 worker + 1 comm) = 40 threads on a
40-PU node. Exactly saturating, so the absent =+ppn= is harmless.

** What went wrong

Step times went bimodal. From the 20-PE workpackage:

#+begin_example
Big step 32 took 1.774660 seconds.
Big step 33 took 2.251789 seconds.
Big step 34 took 146.750683 seconds.
Big step 35 took 155.789841 seconds.
Big step 36 took 155.532061 seconds.
Big step 37 took 1.677535 seconds.
Big step 38 took 1.675546 seconds.
Big step 39 took 151.245140 seconds.
#+end_example

Not a gradual slowdown - a stall, and the sum of ChaNGa's own logged
sub-timings inside those steps is under half a second. The cause is
=+logsize 32000000=, inherited from =leanmd/bench.yml= with no recorded reason.
Reading =deps/charm/src/ck-perf/trace-projections.C=:

- =:157= =pool.reserve(CkpvAccess(CtrLogBufSize))= - the whole buffer is
  reserved at startup. Measured RSS was ~3.3 GB per rank.
- =:494= =flushLogBuffer()= fires only when =pool.size() == pool.capacity()=
  and then calls =writeLog()= *synchronously*: compress the whole buffer and
  write it. Each flush produced ~250 MB of =.log.gz=. Only 7 of the 20 PEs had
  flushed by step 39 and their mtimes were staggered across the stall window.
- It then inserts =BEGIN_INTERRUPT= / =END_INTERRUPT= into the trace, so
  Projections itself treats a mid-run flush as a perturbation to be recorded.
- =:20= the default is =DefaultLogBufSize 1000000=. bench.yml asks for 32x that.

Because every substep ends in a global reduction, one PE stalling to compress
1.5 GB stalls all of them. LeanMD never showed this: its traces never fill even
the default buffer.

Cancelled all three at ~18 min. The 20-PE cell was at step 39 of 128 and would
not have finished inside its =00:40:00=; trace on disk was already 3.2 GB with
most PEs still holding unflushed buffers, against 44 GB of free quota for three
cells. Partial traces deleted - the timings were meaningless anyway.

** What this does *not* fix

Lowering =+logsize= converts rare 150 s cliffs into frequent short pauses. It
does not reduce the total bytes written or the total time spent compressing
them. The run is slow because ChaNGa at 20 PEs genuinely produces tens of GB of
trace over 128 steps, and that is a scope question, not a flag.

** Still open

- Choose the traced scope. The cleanest experiment traces few enough big steps
  that the buffer never flushes at all, so the trace carries no
  =BEGIN_INTERRUPT= gaps: =killAt= stops the run early while leaving =dDelta=
  at its 128-step value, unlike shortening =nSteps=.
- =timelimit= must go up from =00:40:00= regardless; the right value depends on
  the scope above.
- The 4-node cell has still never run.

** Re-run the same day - completed, 3 done / 0 error

=killAt = 17= (16 big steps) with =+logsize= left at 32000000, =timelimit=
01:30:00. Jobs 598731 (1 node) / 598732 (2) / 598733 (4). All three finished;
=jube continue= reports =3 done 0 error= and "Benchmark finished".

*No flush warnings on any workpackage* - =grep -c "Projections log flushed to
disk"= is 0 everywhere, so no buffer filled, no =BEGIN_INTERRUPT= markers, and
Charm++ never disclaimed the timing data. That is the check to repeat after any
change to =killat=, =deta=, the PE counts or =+logsize=.

Step times are steady, with none of the 150 s cliffs of the cancelled run:

| PEs | last 3 big steps (s)   | trace tarball | physics.csv | chare-substeps |
|-----+------------------------+---------------+-------------+----------------|
|  20 | 3.66 / 3.69 / 3.45     | 2.6 GB        | 10.8 MB     |         45 600 |
|  40 | 2.27 / 2.15 / 2.24     | 4.0 GB        | 21.4 MB     |         91 200 |
|  80 | 2.47 / 1.70 / 1.77     | 6.9 GB        | 42.6 MB     |        182 400 |

285 substeps in all three, as expected - the substep structure is a property of
the physics and =dDelta=, not of the PE count. TreePieces scale 160/320/640, so
the sweep totals *319 200 chare-substeps*, inside the plan's 200k-400k target.
All six rungs 0-5 appear in every cell.

Worth noting for future sizing: *trace volume grows with PE count* - 2.6, 4.0
and 6.9 GB for the same 16 steps of the same physics. It is not a fixed budget
split across more logs; more PEs means more messages and more events. Quota
went from 56.3 GB to 66.6 GB of 100 GB for the three cells.

Also worth knowing: JUBE's slurm platform returns as soon as it has submitted,
and =jube info= says "Benchmark not finished" with =#done 0= until =jube
continue= is run to collect the finished jobs. That is expected rather than a
failure.
